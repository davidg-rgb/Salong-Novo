This report consolidates an adversarial team review of Salong NOVO v2 (Astro/Cloudflare). 34 findings survived independent verification; 1 was refuted. Findings are de-duplicated (several were the same defect found from different angles), re-ranked by the verifier's corrected severity, and split into three buckets so it's clear **what breaks today** vs **what to fix before building the admin** vs **doc clean-up**.

Headline: the built public site has **two genuine bugs that ship today** — a draft-post leak and a slug-recompute that breaks live URLs — plus a cluster of latent image/OG defects that are dormant only because no blog post with a cover image is rendered yet. Everything in §10 (the admin panel) is spec-only and unbuilt; its issues are pre-build fixes, not live breakage. The largest theme is the incomplete apex-canonical migration leaving `PUBLIC_SITE_URL`/`PUBLIC_IMAGE_BASE` stale across config.

## A. Real code bugs (in built `src/**` — these are live today)

### A1. [HIGH] Draft (unpublished) blog posts are publicly readable by slug
`getBySlug()` (`src/lib/db.ts:73-83`) selects by `locale + slug` with **no `status='published'` filter**, unlike `listPublished` which does filter (`db.ts:66`). Both blog detail routes (`src/pages/blogg/[slug].astro:9-10`, `src/pages/en/blog/[slug].astro:9-10`) are `prerender=false` and guard only `if (!post) return 404`, and `PostView.astro` has no status check — so anyone who knows or guesses a slug reads a draft's full body and SEO fields before publish. This is an unauthenticated read that bypasses the intended publish gate; the existing `db.test.ts` getBySlug test only covers the not-found case, so it's uncaught. Not critical (no PII/credentials, brochure-blog content, requires knowing the slug) but a real confidentiality bug. **Fix:** add `AND status='published'` to the public `getBySlug` query (or an `isPublished(post)` guard in both detail pages), keeping an unfiltered `getById` only for the future Access-gated admin preview.

### A2. [HIGH] PUT recomputes a published post's slug from its title — breaks stable live URLs (violates AC-6)
The PUT handler at `src/pages/api/admin/posts.ts:85` derives `slug = uniqueSlug(slugify(b.slug ?? b.title ?? "post"), …)` and **never loads the existing row to preserve its slug**. The recent fix added `AND id != ?` (`posts.ts:82-83`) to kill self-collision, but did nothing for immutability: editing a published post's title without resending the original slug silently changes the live URL — exactly what `ARCHITECTURE.md:490` ("frozen once published") and AC-6 (`ARCHITECTURE.md:195`, "a published post's slug never silently changes") forbid. The intended `resolveSlug` fix is spec-only (grep: not in `src/`; `src/lib/slug.ts` exports only `slugify`/`uniqueSlug`). High because this is a live, shippable JSON write endpoint breaking an explicit acceptance criterion. **Fix:** in PUT, load the existing post (`getById`) and, if already published, keep its stored slug regardless of title edits (only an explicit deliberate slug change allowed). *(Note: this same defect is also tracked as the spec-side conflict B7 — the interim uniquify fix must be **deleted**, not layered, when `resolveSlug` lands.)*

### A3. [MEDIUM] Upload trusts client-declared MIME and derives extension from filename — content-type spoofing, no magic-byte check
`src/pages/api/admin/upload.ts` validates against `file.type` (the client-supplied Content-Type, `:29`), stores R2 `contentType` from that same untrusted value (`:34-35`), and builds the key extension from the attacker-controlled `file.name` (`:32`) — with **no magic-byte sniff**. A reaching client can upload arbitrary bytes declared as `image/png` and have R2 serve them back with an attacker-chosen contentType/extension. This is also a doc↔code divergence: `ARCHITECTURE.md:505-506` mandates a `sniffImageType` magic-byte check (415 `content_mismatch`) and ext-from-validated-MIME, neither built. Bounded by Cloudflare Access + optional `ADMIN_API_TOKEN` (`upload.ts:22-24`) gating the route to trusted admins, hence medium not high. **Fix:** sniff PNG/JPEG/WebP/AVIF magic numbers, reject on mismatch, and derive both stored contentType and key extension from the sniff-validated type.

### A4. [MEDIUM] Blog `og:image` is the bare R2 key, not an absolute URL — broken social/OG previews
*(Merged: `lib-api-bugs/og-image-bare-r2-key` + `admin-spec/postview-cover-never-rendered-confirmed`, the OG half.)* `coverImage` is a bare R2 key (`posts.ts:12 "// R2 key"`, minted as `blog/<uuid>.<ext>` at `upload.ts:33`). Both detail pages pass `image={post.coverImage ?? undefined}` (`blogg/[slug].astro:13`, `en/blog/[slug].astro:13`) into `Base.astro:19`, which forwards it **unchanged** to `ogMeta` (note: it *does* absolutize the canonical at `:17` but not the image), and `seo.ts:58-60` emits it verbatim as `og:image`/`twitter:image`. A relative `og:image` resolves against the page origin (`https://salongnovo.se/blog/<uuid>.jpg`) — not where images live — so every blog post with a cover has a broken social card. The helper to fix it already exists (`originalUrl(base,key)`, `images.ts:26`). Medium: limited to social previews, only when `coverImage` is set; on-page render unaffected. **Fix:** resolve the cover to an absolute URL via `originalUrl(env.PUBLIC_IMAGE_BASE, post.coverImage)` before passing it as the OG image (or have `ogMeta` absolutize relative images).

### A5. [MEDIUM] `images.ts` `imageAttrs`/`buildSrcset` emit `-{w}.webp` variant URLs that 404 (latent — no current caller)
*(Merged: `lib-api-bugs/srcset-references-nonexistent-variants` + `admin-spec/imageattrs-404-claim-confirmed`.)* `imageAttrs` (`src/lib/images.ts:51-65`) unconditionally returns `src: variantUrl(...)` and `srcset: buildSrcset(...)`, both resolving through `variantKey → ${stem}-${width}.webp`. No upload-time variant generation exists (`upload.ts:34-40` stores only the original, inserts `variants='[]'`), so every such URL is absent from R2. **Latency is the saving grace:** grep shows `imageAttrs`/`buildSrcset` have zero callers outside `images.ts` — no component renders them today — so this is a shipped, tested-as-correct foot-gun, not a live break. It becomes a live broken-image bug the moment a cover render ships. Medium. **Fix:** until variant generation exists, have `imageAttrs` fall back to `originalUrl(base,key)` for `src` and omit `srcset` (or read the media row's actual `variants` JSON and emit only widths that exist). This is the `responsiveImageAttrs` design in §10.7. *(See also doc-drift C3, which corrects the spec's overstatement that these URLs break "every blog image" today.)*

### A6. [MEDIUM] `upload.ts` returns `previewVariant` pointing at a never-generated WebP variant → guaranteed 404
*(Merged: `lib-api-bugs/previewvariant-guaranteed-404` + `admin-spec/upload-previewvariant-404-confirmed`.)* `upload.ts:49` returns `previewVariant: variantUrl(base, key, 960)` → `${base}/blog/<uuid>-960.webp`, an object the (unbuilt) pipeline never produced; R2 holds only the original. This is the **one genuinely live caller of `variantUrl` today** — a 404 URL surfaced in the admin upload API response right now. `ARCHITECTURE.md:509-510` already says this field must be removed for exactly this reason; the built code still emits it. Medium: the consuming admin editor UI is unbuilt, so nothing follows the URL yet. **Fix:** drop `previewVariant`; return the served original (`originalUrl(base,key)`) as the preview.

### A7. [MEDIUM] Blog post hreflang/x-default alternates point to the blog *index* of both locales
Blog posts are single-language by decision, but every post page renders `<Base pageKey="blog">` (`blogg/[slug].astro:13`, `en/blog/[slug].astro:13`). `Base.astro:18` derives alternates from `alternates(pageKey)`, which for `"blog"` returns only the two **index** slugs (`/blogg`, `/en/blog`) (`routes.ts:44-46`). So an SV post at `/blogg/min-artikel` emits `hreflang=en → /en/blog` (falsely declaring the EN blog index as the EN translation of the SV post) and `x-default → /blogg`, while omitting the post's own URL — and the canonical (correctly the post URL, `Base.astro:17`) disagrees with x-default. Reciprocal hreflang is broken. Corrected high→medium: canonical is correct so the post stays indexable under its own URL; damage is degraded/non-reciprocal hreflang signals, not a broken user path. **Fix:** for `[slug]` pages, suppress cross-locale hreflang (add a `Base` prop, e.g. `alternates?: {locale,path}[]` or `selfCanonicalOnly`, so the page passes self-only alternates and skips x-default/other-locale links); index pages keep current behaviour.

### A8. [MEDIUM] Staff modal never receives focus on open — `getElementById("sm-close")` targets a non-existent id
In `src/components/StaffGrid.astro`, the close button is declared `class="sm-close"` (no id) at `:33`, but the modal `open()` handler calls `document.getElementById("sm-close")?.focus()` at `:57`. No element has `id="sm-close"`, so the optional chain short-circuits and focus is never moved into the `role="dialog" aria-modal="true"` container. There's no focus-trap or focus-restore either (script `:42-65`), so keyboard/screen-reader users who open a stylist card stay focused on the now-visually-behind trigger — breaking the accessible-dialog contract. Escape- and click-to-close still work, so AT users are degraded, not fully trapped. Real a11y defect on the primary staff interaction. **Fix:** add `id="sm-close"` at `:33` or change `:57` to `modal.querySelector('.sm-close')?.focus()`; ideally add a focus-trap + restore-focus-to-trigger.

### A9. [LOW] Blog post `coverImage` is used for OG meta but never rendered in the article body
*(Distinct from A4: A4 is the *broken* OG URL; this is the *missing on-page* render.)* Both detail pages pass `image={post.coverImage}` to `Base` for OG, but `PostView.astro:9-17` renders only back-link, meta, h1, and the markdown body — it never references `post.coverImage` as a hero `<img>`. A post with a cover shows it on social shares but never on the page itself; for a "fashion-magazine brochure site" that's a visible content gap. Low because it's likely deferred to the visual-design gate (`ARCHITECTURE.md:715-717` names exactly this as the planned 4d fix). **Fix:** render the cover before the h1 when present, or document explicitly that cover is OG-only by design.

### A10. [LOW] Blog post detail pages lack the `.catch()` guard the index has — a D1 error 500s instead of a graceful 404
The blog index degrades gracefully: `listPublished(db, locale).catch(() => [])` (`blogg/index.astro:9`). Both post-detail routes call `await getBySlug(db, locale, slug)` with **no** `.catch` (`blogg/[slug].astro:9`, `en/blog/[slug].astro:9`); `getBySlug` returns null only on a missing row, but rejects on a transient D1 error, which the `if (!post) return 404` branch doesn't cover — yielding a 500. Inconsistent error handling across three routes on one data source. Low: only manifests during a D1 outage, when the site is already degraded and 500-vs-404 is cosmetic. **Fix:** mirror the index — `getBySlug(...).catch(() => null)` in both SV and EN routes so DB errors fall through to the 404.

### A11. [LOW] `stripLocale` assumes same slug across locales — returns a non-existent SV path for divergent slugs
`stripLocale` (`src/i18n/routes.ts:55-61`) only strips the leading locale segment and rejoins; it never translates the slug. So `stripLocale('/en/about')` returns `/about`, but the SV page is `/om-oss` (`ROUTES.about = {sv:'om-oss', en:'about'}`) — and the same holds for staff, services, work/careers, awards, blog. Currently dormant: grep shows no `src` caller (hreflang uses `alternates(pageKey)` via `Base.astro:18`, which resolves per-locale correctly). Low: a latent trap if anyone later uses it to derive the SV equivalent of an EN URL. **Fix:** document it as "locale-prefix removal only, not slug translation," replace its intended use with a `pageKey`-based resolver, or delete it (no real consumer).

### A12. [LOW] `listPublished` filters `status` but not `published_at IS NOT NULL` — a published+null row renders with no date
`listPublished` (`db.ts:58-71`) filters `WHERE status='published'` and orders by `published_at DESC` with no `published_at IS NOT NULL` guard. The insert/update helpers (`db.ts:129,160`) guarantee `published_at` is set whenever `status='published'`, so normal flow is fine — but any row written out-of-band (manual SQL, import, future bug) with `status='published'` and `published_at=NULL` would surface in the public list, sort to the bottom, and render a blank date (`PostView.astro:12` → empty span). The index `(locale,status,published_at DESC)` implies the date is meant to be present. Low: defensive robustness, not a live defect; consequence is cosmetic. **Fix:** add `AND published_at IS NOT NULL` to `listPublished`.

## B. Spec issues (ARCHITECTURE.md §10 — the admin panel, not built yet)

These are not live breakage. They are correctness/consistency problems to resolve **before** building the admin so the build doesn't bake them in. Several are direct consequences of the incomplete apex-canonical migration.

### B1. [MEDIUM] §10.8 CSRF guard is wired to `PUBLIC_SITE_URL` (www) while admin is served on the apex — would 403 admin writes on the Origin-fallback path
*(Merged: `admin-spec/csrf-siteurl-www-apex-mismatch` + `cross-cutting/wrangler-env-still-www`.)* The apex migration moved `site` to `https://salongnovo.se` (`astro.config.mjs:10`) and the admin/Access surface lives on the apex (`ARCHITECTURE.md:289`), but `PUBLIC_SITE_URL` still reads `https://www.salongnovo.se` in **both** `wrangler.toml:23` and `.env.example:5`. §10.8 (`ARCHITECTURE.md:741`) specs the CSRF guard as `isSameOriginWrite(request, env.PUBLIC_SITE_URL)`. If built against the stale www value while the site serves on apex, the Origin-comparison path would 403 legitimate admin writes. Corrected high→medium: (a) the guard *prefers* `Sec-Fetch-Site` (sent by all modern browsers), which passes regardless of host — only the older-browser `Origin` fallback compares against `PUBLIC_SITE_URL`, so it is **not** "every admin write"; (b) the var has zero runtime consumers today (grep: only `env.d.ts:7`) and `isSameOriginWrite` doesn't exist in `src/` — spec-only, no live break. **Fix:** set `PUBLIC_SITE_URL` to `https://salongnovo.se` in both files; have `isSameOriginWrite` tolerate the www↔apex pair (or rely on the www→apex 301 so Origin is always apex); add `PUBLIC_SITE_URL` to a §10 deploy-invariant list. *(Note: the `PUBLIC_IMAGE_BASE="img.salongnovo.se"` value in the same files is a **separate** issue — see B2 — not a www leftover.)*

### B2. [MEDIUM] `PUBLIC_IMAGE_BASE` ships the Stage-B `img.salongnovo.se` value while §8/§10 require `""` for the Stage-A launch
*(Merged: `cross-cutting/image-base-stage-a-vs-shipped` + `admin-spec/image-base-stage-a-contradiction`.)* `ARCHITECTURE.md:137,847,936,959` repeatedly mandate launching with `PUBLIC_IMAGE_BASE=""` (Stage-A same-origin `/api/media/*` serving, zero DNS/R2-domain setup), cutting over to `img.salongnovo.se` only at the deferred Stage B. But `wrangler.toml:24` and `.env.example:8` already ship the Stage-B value. Blast radius is narrower than first claimed: the public `servedUrl` render path (`src/lib/media.ts`) and the `/api/media/[...key]` route don't exist yet (spec-only), so the *current* consumer is only `upload.ts:43-49` — an admin uploading would get a broken `https://img.salongnovo.se/...` preview URL (no bucket attached at launch), admin-only and pre-launch. Medium: a real latent config-vs-spec break that bites at the documented Stage-A launch. **Fix:** set `PUBLIC_IMAGE_BASE=""` in both files now; flip to the img domain only at the Stage-B cutover (already a tracked step at `ARCHITECTURE.md:847` / sub-phase 4d).

### B3. [MEDIUM] `toInput` silently defaults a bad/missing locale to `"sv"` — in **both** POST and PUT
The current handler coerces an invalid or missing locale to Swedish: `const locale: Locale = b.locale && isLocale(b.locale) ? b.locale : "sv";` at `posts.ts:39` (POST via `toInput`) **and again** at `:77` (PUT, inline). §10.5 (`ARCHITECTURE.md:467-468`) correctly specs `parsePostWrite` to reject with `invalid_locale` and "no silent 'sv' default" — but the spec text only names `toInput`, while the defect is duplicated in the PUT path. Silently writing wrong-locale data masks client bugs. Medium (admin is Access-gated, trusted staff). **Fix:** apply `parsePostWrite`'s `invalid_locale` rule, and ensure the builder replaces **both** the POST and PUT coercion sites, not just `toInput`.

### B4. [MEDIUM] §8 deploy checklist cites `assertNoDevBypassInProd` / `ACCESS_*` / `DEV_ADMIN_EMAIL` as active deploy steps, but none are built
§8 step 4 (`ARCHITECTURE.md:138`), which sits in the in-scope §1–§9 deployment section, tells the deployer to set `ACCESS_AUD`/`ACCESS_TEAM_DOMAIN` and states `DEV_ADMIN_EMAIL` absence "is enforced by `assertNoDevBypassInProd`." But all of `assertNoDevBypassInProd`, `ACCESS_AUD`, `ACCESS_TEAM_DOMAIN`, `DEV_ADMIN_EMAIL` appear **only** in `ARCHITECTURE.md` (grep), `src/lib/access.ts` doesn't exist, and `env.d.ts` declares none of them — they're §10 spec-only. The built admin auth (`posts.ts:11-15`) is just an optional `ADMIN_API_TOKEN` header check. So §8.4 presents an unbuilt guarantee as an active deploy step, blurring the built/spec line the doc claims to keep. Medium (doc-drift, nothing to misconfigure since the enforcement doesn't exist). **Fix:** mark the Access/JWT/dev-bypass parts of §8 as `(after §10 admin build)` or move them into §10's deploy steps.

### B5. [MEDIUM] §4 claims every core module is unit-tested, but `db.ts`'s `updatePost`/`deletePost`/`listAll` have zero tests
§4's heading (`ARCHITECTURE.md:78`) is "Core modules … — all unit-tested," and the table (`:88`) maps `lib/db.ts` to `db.test`, with the design principle "all logic that *can* be pure and testable *is*" (`:94`). But `tests/db.test.ts` imports only `mapRow, listPublished, getBySlug, insertPost`; the three exported, production-used functions `updatePost` (`db.ts:136`, used by PUT), `deletePost` (`:167`, used by DELETE), and `listAll` (`:86`, the admin dashboard query) are never imported or exercised. `updatePost` carries the byte-identical `published_at` transition logic that `insertPost` has a dedicated test for, yet has none. The "all unit-tested" claim is materially overstated. Corrected high→medium: a coverage/trust gap, not a proven runtime break. **Fix (per prime directive):** add `db.test.ts` cases for `updatePost` (assert published_at transition + binds + `WHERE id`), `deletePost`, and `listAll` (assert `ORDER BY updated_at DESC`) — rather than softening §4's wording.

### B6. [MEDIUM] Spec correctly flags `PostView` never renders the cover — but the *fix* doesn't resolve `og:image` to absolute
§10.7 (`ARCHITECTURE.md:716`) correctly says `PostView` "currently only passes coverImage as the OG image" and never renders it, and its `responsiveImageAttrs` fix renders the visible cover. But the spec's fix addresses only the *visible* cover and **does not** also resolve the OG image to an absolute URL — leaving the live A4 bug (`og:image` = bare R2 key) unaddressed in the planned change. Medium. **Fix:** extend the §10.7 PostView fix to absolutize the OG image via `originalUrl(base,key)` before passing to `Base`/`ogMeta`, not just render the visible cover. *(Pairs with live bug A4 and doc-drift C4, which notes the §10.7 parenthetical misdescribes where the OG wiring actually lives.)*

### B7. [LOW] §10.6 `resolveSlug` (immutable-after-publish) must **replace**, not layer onto, the interim PUT uniquify fix
The just-applied PUT uniquify fix (`posts.ts:85`) recomputes the slug from title every update (the live A2 bug). §10.5/§10.6 spec `resolveSlug` to **freeze** a published post's slug. They don't conflict destructively — `resolveSlug` supersedes the current logic — but the spec must be explicit that 4c **deletes** `posts.ts:77-85`, not layers `resolveSlug` on top. Corrected medium→low: §10.10 4c already says "resolve slug via resolveSlug+getById+takenSlugs" (`:826`) and its Accept clause (`:837`) tests "editing a published post's title does not change its slug (AC-6)," so a builder has the directive plus a failing acceptance test that catches the exact layering mistake. Residual is a mild doc-precision request. **Fix:** in §10.10 4c, state plainly that the existing PUT slug block is deleted and replaced by `resolveSlug(existing, override, takenSlugs)`.

### B8. [LOW] §5/§10.4 data model says `media.post_id` links uploads to posts, but built `upload.ts` never sets `post_id`
§5 (`ARCHITECTURE.md:107`) centers the media model on `post_id REFERENCES posts(id)` (`migrations/0001_init.sql:28`, `ON DELETE SET NULL`), but the built `upload.ts:37-41` INSERT omits `post_id` entirely (only `r2_key, alt, variants, created_at`), so every upload lands orphaned (`post_id NULL`). Consistent with the §10.5 future plan (`postId` optional, association-at-save in §10.7) and §5 never claims upload auto-links — schema tolerates NULL, no corruption. Low. **Fix:** no action on the built core; ensure §10's `upload.ts` CHG is where the optional `postId` binding is reconciled, and that §5 doesn't imply uploads auto-link.

### B9. [LOW] §10.5 says `insertPost`/`updatePost` return `void`, requiring a real "return full Post" change — mechanism under-specified for `updatePost`
Both are currently `Promise<void>` ending in `.run()` with no `RETURNING` and no `lastrowid` read (`db.ts:107,136`), so the editor can't learn the new id — exactly the gap §10.5 addresses (`:486` insertPost "RETURNING * → Post"; `:492`/`:929` updatePost "returns Post"). The claim is correct, not contradictory. Minor precision gap: §10.5:486 *does* spell out `RETURNING *` for `insertPost`, but `updatePost` only says "returns Post" without naming the mechanism — a builder could keep `.run()`. Low. **Fix:** in §10.11's db.ts change row, state that both insert/update must append `RETURNING *` and read via `.first<PostRow>()` then `mapRow` (the pattern already exists at `db.ts:81-82`).

### B10. [LOW] §10.5 names `toInput` for the "author default," but that function is being removed and the precedence belongs in the route handler
§10.5 (`ARCHITECTURE.md:541`) says "`toInput`/`parsePostWrite` take the authenticated user so a writer never types their email." But the spec deletes `toInput` (replaced by `parsePostWrite`, which §10.4 mandates *pure/env-free* — so it can't read `locals.user`), and the editor serializer is `toApiBody` (`:591`, client-side, no `locals`). The author precedence (`body.author → locals.user?.email → ""`) belongs in the POST/PUT route handler, where `locals` is available. Referencing `toInput` points a builder at a function that won't exist. Low (doc-only, unbuilt section; the precedence rule itself is stated correctly). **Fix:** reword §10.5 to put precedence in the route handler after `parsePostWrite`; drop the `toInput` reference; keep `parsePostWrite` user-free.

### B11. [LOW] §10.11 env.d.ts change row + §8 checklist never call out `PUBLIC_SITE_URL` as deploy-critical for the §10.8 CSRF guard
No missing-declaration bug — `PUBLIC_SITE_URL` is already declared (`env.d.ts:7`) and §10.11:928 correctly lists only *new* vars. But the env-var story is scattered: env.d.ts declares it, §10.8 consumes it for `isSameOriginWrite`, and §8's deploy checklist (`:136-138`) lists `ACCESS_AUD`/`ACCESS_TEAM_DOMAIN`/`ADMIN_API_TOKEN`/`PUBLIC_IMAGE_BASE` but **omits** `PUBLIC_SITE_URL` despite §10.8 needing it correct (the B1 footgun). Low (doc-organization, not a defect), but an operational footgun: a wrong `PUBLIC_SITE_URL` 403s valid admin writes with no checklist warning. **Fix:** add a single §10 env-var table (or extend §8 step 4) listing every var §10 depends on and its required prod value — explicitly `PUBLIC_SITE_URL=apex` (CSRF) and `PUBLIC_IMAGE_BASE=""` (Stage A). This closes the scatter and makes B1/B2 impossible to miss at deploy.

## C. Doc-drift (ARCHITECTURE / config claims that don't match the code)

### C1. [LOW] `wrangler.toml` `PUBLIC_SITE_URL` still points at www after the apex canonical switch
*(This is the config-coherence facet; the security consequence is B1.)* The apex migration updated `astro.config.mjs:10` (and `Base.astro`/sitemap/robots all derive the host from `Astro.site`, now apex), but `wrangler.toml:23` still reads `https://www.salongnovo.se` (and `.env.example:5` has the same stale value). Currently inert — no `src/` runtime consumer (grep: only `env.d.ts:7`). Corrected high→low: a latent doc/config inconsistency, not a live split-host break. **Fix:** set `PUBLIC_SITE_URL` to the apex in both files (same edit as B1).

### C2. [LOW] `tests/seo.test.ts` still passes the old www host to `hairSalonJsonLd` (stale, but does not fail)
`tests/seo.test.ts:5` constructs the JSON-LD with `hairSalonJsonLd("https://www.salongnovo.se")`. It passes (suite green) only because the test never asserts the `url` field that argument feeds (`seo.ts:13`). Stale and misleading after the apex switch; any future `expect(ld.url)` would lock in the wrong host. Low (test-hygiene). **Fix:** update the literal to `https://salongnovo.se`, and optionally add `expect(ld.url).toBe("https://salongnovo.se")` to pin the canonical host.
